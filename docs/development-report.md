# 映章 YingZhang 开发报告：把“生成一份 PPT”做成可核查、可编辑、可恢复的工程流程

> 项目地址：[GitHub · yingzhang-ai-ppt](https://github.com/star031104/yingzhang-ai-ppt)
> 技术栈：FastAPI、React、TypeScript、SQLite、Playwright、PptxGenJS、python-pptx
> 本文描述当前公开仓库的实现与边界。演示内容和版式仍应由使用者做最终审阅。

很多 AI 演示工具能很快生成一份看起来完整的幻灯片。但当材料里有具体数字、来源限制和真实交付要求时，“能生成”只是起点：页面写出的结论从哪里来？模型把同比增长改写成绝对增量怎么办？某页排版在浏览器里正常，打开 PowerPoint 后挤出画布怎么办？生成到第十页服务中断，是否只能重来？

我做映章，是想把这些问题放进同一条可追踪的生产流程。系统不把模型回复直接当作成品，而是让材料、证据、叙事、页面契约、视觉候选、人工决策和最终交付各自留下可以检查的结果。它是一套本地优先的 AI 演示工作台，也是一项关于“如何把不确定的生成过程变成可维护软件”的工程实验。

## 一、起点：真正难的不是让模型写出十二页

最简单的做法，是把用户上传的文件转成文本，拼进提示词，让模型返回一组标题和要点，再套模板导出 PPTX。这条链路容易演示，也容易在真实材料前失控。

- 原文的表格行、单位、时间范围和注释在纯文本里被压平；“增长 12%”可能失去基期和口径。
- 模型会为叙事补上材料中没有的数字、案例或结论。
- 一种模板从头用到尾，数据页、问题页和结论页只有颜色变化，没有信息结构变化。
- 导出成图片虽然整齐，却让交付后的图表、表格和文字无法正常编辑。
- 长任务中断后，前端显示的进度与磁盘上真正完成的页面可能不一致。

因此，映章的目标从一开始就不是“给一句话，自动吐出一份漂亮 PPT”。更准确的目标是：**让用户能够用自己的材料生成演示，并知道每一页为什么这样写、如何修改、能否可靠交付。**

## 二、设计原则：让概率模型负责提案，让确定性程序守住边界

模型擅长概括、改写、提出结构和视觉方向；它不适合单独承担事实权威、文件系统操作或发布决策。映章把工作拆成两类。

模型参与叙事规划、页面角色建议、文案压缩与候选视觉提议。确定性程序负责来源定位、数值检查、页面预算、任务状态、文件权限、版本修订和交付门禁。没有材料支持的事实不应因为“听上去合理”就进入图表；用户已经选定的页面也不应因为后台任务重试而被悄悄覆盖。

这决定了系统的基本路径：**先理解材料，再形成证据；先明确页面职责，再生成页面；先检查结果，再导出交付。** 人工审阅贯穿其中，不被视为生成失败后的补救措施。

## 三、从材料到证据：保留结构，而不是只保留文本

映章接收 PDF、Word、Excel、PPTX、Markdown、HTML、CSV 和常见图片。解析阶段保留章节层级、表格行列、数字单位、图片与来源位置，并把读取失败、扫描页、缺失计算值和内容截断等风险显式呈现给用户。

例如，一份经营报告中写着“2025 年第四季度收入 1.2 亿元，同比增长 8.4%，不含一次性收入”。这里的时间、单位、百分比口径和限定条件不能拆散。映章会把数值声明与原始材料建立绑定；页面要把它变成图表时，需要有对应的系列、单位和来源，不能凭标题就补出前三季度数据。材料里没有的比较基线，也不能由模型臆造。

系统同样保留学术材料中的研究对象、方法、实验结果与局限。数字不是“越大越适合做视觉主角”；模型名称、章节编号和参考文献标记不应被误认成可展示的指标。这样的约束减少了表面上漂亮、实际含义错误的页面。

## 四、叙事与页面契约：先回答“这一页做什么”

材料理解之后，系统根据演示目标、受众、时长、风格和页数预算组织大纲。每页有自己的角色、核心主张、证据引用、视觉意图、布局区域、文字预算与对象上限。数据页、对比页、流程页、封面和结尾页分别拥有不同的内容与视觉约束。

这里有一个重要取舍：页面契约要足够具体，能够约束后续生成；也要留有候选空间，让系统在同一份证据上尝试不同布局。映章会生成多个候选，测量文字溢出、重叠、层级和内容适配度，再把可选择的方案交还给用户。修改页面后，候选与导出文件的内容指纹也会变化，旧候选不能混入新版本。

生成不再是一条只能从头跑到尾的黑盒。用户可以先确认大纲，再检查代表页样张，随后生成全套页面；也可以单页重生成、对象级修改、回滚页面版本，并保留已经人工选择的结果。

## 五、为什么采用 HTML 场景与可编辑 PPTX 的双重交付

只用 PowerPoint 原生对象排版，复杂页面的实时预览与测量成本较高；只输出 HTML 截图，又会牺牲交付后的可编辑性。映章选择让浏览器承担页面预览和几何测量，再把页面语义编译到 PPTX。

浏览器负责计算文字与元素的位置，场景数据作为布局的共同依据。图表、表格、时间线、流程和关系结构优先保留为 PowerPoint 可编辑对象；确实无法等价表达的视觉元素才栅格化。PDF 与 HTML 用于预览和分发，PPTX 用于继续编辑与正式演示。导出后还要检查页数、标题、内容覆盖和重要对象是否保留。

这个方案不是对所有 Office 软件“像素级一致”的承诺。复杂公式、特殊字体、既有动画和第三方渲染器仍会造成差异；重要交付必须在目标 PowerPoint 或 WPS 环境里打开检查。工程能降低风险，但不能代替最后一公里的人工判断。

## 六、长任务如何变得可恢复

生成一份演示可能经过材料读取、模型规划、样张、逐页候选、质量检查和导出，期间任一环节都可能超时或失败。为了避免“网页显示成功，文件却没有保存”的状态错位，SQLite 中保存任务的完整快照和检查点；实时事件只负责加速展示，不是唯一事实来源。

用户重新打开页面时，客户端先读取持久化快照，再订阅实时进度；连接中断时可退回轮询。工作流节点有明确的输入、输出、重试边界和产物记录。服务重启后，仅在重建上下文完整时恢复任务；取消操作在安全边界发生，而不是任意中断正在写入的文件。页面写入带修订号，过期客户端的更新会被拒绝。

目前的本地执行器只支持单进程、单实例。它适合个人工作台与受控测试，不应通过简单增加 Uvicorn worker 数来假装完成分布式扩容。真正多实例化需要共享队列、任务租约与事件设施，这是刻意保留的架构边界。

## 七、本地优先不是“没有安全问题”

项目、材料和生成产物默认留在当前设备；模型凭据优先放在系统密钥环，必要时使用本地加密文件回退。仓库忽略 `.env`、`runtime/`、数据库、日志和生成结果，克隆仓库不会带出作者的个人工作区。上传大小、外部地址获取和第三方技能安装也设有服务端约束；技能脚本默认不执行。

但本地运行与公网服务是两种不同风险模型。公网测试模式需要会话、限额和可信代理边界；独立账号模式需要项目成员权限。反向代理、HTTPS、备份、密钥管理和审计策略仍是对外部署者的责任。系统不把“打开了公网隧道”当成“已经具备互联网生产环境安全性”。

## 八、个人化为什么必须可暂停、可导出、可遗忘

演示工作有明显的个人风格：同一个人可能偏好某种标题长度、图表密度或叙事节奏。映章可以根据用户确认过的修改、参考稿和场景设置形成经验建议，但这类经验只能帮助下一次创作，不能凌驾于本次材料的证据之上。

个人化数据默认保存在本机；用户可以暂停学习、导入导出、删除单条经验、按场景清除，或恢复空白工作区。首次克隆没有作者的个人偏好。这些操作与“推荐得准不准”同样重要：如果经验来源不清、无法纠正或无法删除，长期使用的系统会逐渐把旧选择误认为不可修改的规则。

## 九、导出与发布为什么是两道门

导出意味着生成文件；发布意味着对外确认一个具体版本。映章把页面修订、人工审批和发布快照关联起来：最终批准记录当时的页面数据与渲染文件摘要；批准后继续修改页面，就必须重新审阅，不能让旧批准覆盖新内容。

这个边界也约束了“自动修复”。程序可以提示溢出、缺失来源或对比度不足，也可以提出候选修改；但事实判断、许可确认和最终发布决定仍由人承担。否则，系统很容易在最后一步把“机器认为可用”误写成“负责人已经同意”。

## 十、技术选型与工程结构

后端使用 FastAPI 提供项目、材料、页面、任务、审核与交付接口；SQLAlchemy 和 Alembic 管理 SQLite 数据及前向迁移。前端使用 React、TypeScript 和 Vite，页面按业务域组织，API 客户端拆为类型、HTTP 传输、项目操作以及模型/技能操作。演示引擎独立放在 Node 包中，利用 Playwright 做真实浏览器渲染，并用 PptxGenJS 输出可编辑 PPTX。

这个组合没有追求技术栈的数量。SQLite 与本地文件系统降低个人部署门槛；真实浏览器给排版检查提供可观测结果；独立渲染包让服务端的业务状态与文件格式细节保持边界。系统仍有较大的生成编排模块，后续扩展应继续按业务契约渐进拆分，而不是为了文件短小打散事务和恢复逻辑。

仓库保留一份描述当前实现的[工程架构说明](architecture.md)，不再把一系列按阶段命名、内容重复的旧决策文件当作维护入口。数据库迁移、自动化基准和测试材料则仍然保留，因为它们分别承载升级路径、回归检查和人工验收，不属于可以随意删除的“旧版本”。

## 十一、质量门禁：验证产物，而不只验证接口返回

项目把质量验证分成几层：Python 测试覆盖权限、材料理解、数值声明、任务恢复、版本、交付和安全边界；前端测试覆盖关键交互；演示引擎测试检查浏览器页面与原生 PPTX；学术、商业、数据和产品四类基准材料用于持续观察内容覆盖、候选多样性、可访问性和交付质量。

CI 从空白数据库执行迁移，安装真实浏览器后运行测试与构建，并使用 LibreOffice 对四类基准演示做 PPTX 到 PDF 的往返渲染，核对页数与每页标题。依赖审计阻止已知高危 Node 依赖进入发布路径。当前本地验证包括 189 项后端测试、10 项网页测试和 44 项演示引擎测试；这些数字是验证记录，不是“任何材料都能生成专业演示”的保证。

我更关心失败是否会被准确暴露：扫描材料无法识别、证据不够、版面拥挤、外部素材许可不清或 Office 渲染偏差，都应该作为可见问题留给用户处理，而不是被一句“生成成功”掩盖。

## 十二、从能运行到能维护：这次工程收敛

随着项目增加材料理解、页面编辑、模型配置、治理与交付，早期的单文件入口开始承担过多职责。这次整理没有重写整条生产链，而是把前端 API 的数据类型、HTTP 传输、项目操作和模型/技能操作分开；把后端生成路由里的受众文案清理、证据筛选和数值核验提取为独立模块。接口名称和行为保持原样，再用现有测试验证拆分没有改变用户流程。

文档也采用同样的原则：保留描述当前系统的架构说明和可复现基准，清除只记录阶段编号的旧决策片段、未被使用的导出样例及被新检查覆盖的脚本。真正不能删的是数据库迁移和回归材料：前者决定已有工作区能否升级，后者决定下一次修改能否发现退化。清理的目标是减少维护者需要猜测的入口，不是让仓库看起来文件越少越好。

## 十三、做完整个系统后，仍然需要承认的边界

映章当前适合本地体验、功能验证和逐步打磨的正式创作。自动 OCR 无法保证识别所有扫描文件；模型可能误读事实；复杂品牌字体和 Office 特性需要人工修复；网络素材的版权、商标和肖像授权不能由程序替用户决定。首次公开版本的接口和数据结构也可能继续调整。

我不把这些限制写成免责声明后就算完成。它们反过来规定了产品行为：材料读取要报告缺口，数字要保留口径，导出要有可检查产物，长任务要能恢复，发布前要有人审阅。对演示软件来说，真正的“专业”不是替用户做掉所有判断，而是让每个重要判断有依据、能修改、能回溯。

映章想验证的就是这一点：**AI 可以加速从材料到演示的过程，但可信交付来自清晰的证据链、受约束的生成、可编辑的文件和可重复的工程检查。**
